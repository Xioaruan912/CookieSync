# WebDAV 使用说明

## 安装

使用发布 ZIP 时先完整解压。在 Chrome 打开 `chrome://extensions`，开启右上角的“开发者模式”，点击“加载已解压的扩展程序”，选择包含 `manifest.json` 的文件夹。两台电脑各安装一次。

从源码构建：Node.js 20.12+、pnpm 9.1.1，执行：

```sh
node scripts/workspace.mjs verify
```

依赖、构建与检查均在系统缓存中运行；源码文件夹不产生 node_modules、dist 或 .turbo。默认输出到源码旁的 `CookieSync-release/`，ZIP 为正式安装包，`unpacked/` 可直接加载。可用 `build` 代替 `verify` 对已验证源码打包；`--cache` / `--output` 只接受源码外路径。修改源码后重新打包，用户下载并手动重新加载扩展；没有开发自动重载服务。

也可从仓库 [最新 Releases](https://github.com/Xioaruan912/CookieSync/releases/latest) 的 Assets 下载 **CookieSync-chrome-版本号.zip**，下载后解压加载。Code → Download ZIP 和 Release 中的 Source code 是源码，不是安装包。

## 配置

1. 点击扩展的齿轮，选择 WebDAV。
2. 填写 WebDAV **目录最终地址**，例如 `https://dav.example.com/remote.php/dav/files/alice/`。不要填共享链接、登录网页或含账号密码的 URL。不跟随重定向；如遇连接失败，填写重定向后的实际 WebDAV 地址。要求 HTTPS，有效受信任证书；仅 `localhost` / `127.0.0.1` / `[::1]` 允许 HTTP 本机测试。
3. 填写用户名与密码。优先使用专用的、可撤销的应用密码。
4. 填写相对于 URL 的远程文件路径，例如 `CookieSync/cookies.txt`。先在服务器创建 `CookieSync` 目录；扩展不自动创建目录。开头的 `/` 仍按相对路径处理；中文、空格、`#` 等自动编码，填写未编码的路径。两台电脑 URL、账号、路径必须一致。
5. 点击“测试连接”。扩展会在同目录创建随机后缀 `.connection-test-…` 文件，验证创建、覆盖写入、读取和删除后清理；不会覆盖同步文件。测试失败时检查读、写、删除权限以及是否支持 Basic Auth。连接测试不代表远程同步数据格式或加密密码正确。
6. 点击“保存并使用 WebDAV”。默认凭据只保存在本机；如需两台电脑免重复配置，主动勾选“使用 Chrome / Google 账号同步此 WebDAV 配置”，然后保存。此操作包含应用密码，需保护 Google 账号；两端 Chrome 需开启同账号同步并具有相同扩展 ID。详见 [Google 同步与一次迁移](GOOGLE.md)。此存储不是操作系统保险箱，本机用户或恶意软件仍可能读取。

WebDAV 的远程文件路径独立于“高级设置”的存储键。需要多套账号时，分别使用不同的远程文件路径。原有 Cloudflare KV 与 GitHub Gist 入口保留（Gist 的 OAuth 授权仍使用原项目应用配置，解压安装版本可能受其回调地址限制），切换回对应后端需在其页面保存或授权。

## 小红书、抖音、115 网盘优先支持

对 `xiaohongshu.com`、`douyin.com`、`115.com` 及其子域，推送采集整个主域下的 Cookie，恢复时允许同网站子域的登录 Cookie，保留 HttpOnly、Secure、SameSite、Path 等属性。不会把相似但不属于该网站的域名混入。针对原 Protobuf 会话 Cookie 的过期时间默认值为 0 的情况，恢复时不设置过期时间，避免登录 Cookie 刚写入即删除；真正已过期的持久 Cookie 不会恢复。

在这三个网站的弹窗中可选择“此电脑主要发送”或“此电脑主要接收”，分别开启自动推送或自动拉取。角色设置按网站生效。其他网站也会自动发现，无需先手动推送，可在同步管理中逐站关闭自动收发。LocalStorage 仍按当前页面来源采集，不会跨所有子域批量采集。未对用户真实账号执行登录成功率测试；网站服务端撤销、设备绑定或二次验证无法由扩展保证解决。

## 两台电脑同步

先在电脑 A 登录网站，打开网站页面，点击扩展的“推送并合并 Cookie”。再在电脑 B 打开同一网站，点击“拉取并应用 Cookie”；页面会刷新。包含 LocalStorage 时，两端使用同一网站主机名，例如都使用 `www.example.com`。同一个网站账号请按顺序操作，避免两台电脑同时改写。

**合并规则**：每次 WebDAV 推送先读取远程文件，保留其他网站，使用本机当前网站的 Cookie/LocalStorage 快照替换同网站数据。不是按单个 Cookie 时间戳合并，也不自动合并两个不同账号。同域较旧的本机快照仍可能覆盖较新的远程登录，推送前请确认当前登录状态。

服务器返回强 ETag 时，写入使用 `If-Match`，新建使用 `If-None-Match: *`。遇到 412 会停止覆盖；原因可能包括远程版本变化、文件锁或服务器不兼容条件写入，不能仅凭 412 判断另一台电脑修改了文件。服务器不提供强 ETag 时，默认阻止覆盖已有文件。只有明确勾选“AList / OpenList 等网关兼容模式”才停用条件写入。兼容模式在上传前重新读取并检查内容是否变化，但检查与 PUT 之间并非原子操作，仍可能丢失另一台设备的并发更新。服务器忽略条件请求时同样无法保证并发安全。不会自动盲目重试冲突。

**无感同步**默认开启，可在高级设置关闭启动拉取或后台同步，并调整后台间隔（默认 2 分钟，范围 1～60 分钟）：

- 默认自动发现普通窗口中访问过的 HTTP(S) 网站（包括已打开的页面）：存在 Cookie 或启用的 LocalStorage 时自动登记并开启收发，无需先手动推送。首次成功读取远端后建立变化基线；远端没有该站点数据时再采集本机。无法可靠识别登录状态，未登录页面也可能产生 Cookie；不会批量登记未访问的 Cookie 域名或无数据页面。设置中可关闭新站点发现；用户明确关闭的站点开关会保留。明确设为只发送的网站不会在启动时被远程数据覆盖。
- 浏览器资料首次启动时（`runtime.onStartup` 加每会话首次后台唤醒兜底），先尝试发送上次未完成的本机队列，再从远程恢复 Cookie；若某网站仍有未上传改动，会跳过其启动恢复，防止被旧远程数据覆盖。远程已登记的网站默认纳入自动收发。浏览器后台仍运行时只重新打开窗口不一定触发资料启动事件；已启用网站的页面就绪后也会触发拉取。
- Cookie 变化时仅采集并保存本机队列，不立即请求服务器。后台按设置间隔合并上传，默认自动上传尝试不超过每 2 分钟一次；启动重试和用户手动操作不受此限。没有改动时不上传。
- 页面内约每 30 秒检查一次本机状态。尚未登记的页面会重新尝试发现，以覆盖加载后才生成 Cookie / LocalStorage 的登录场景；新站点登记后触发后台合并检查。已登记页面的 LocalStorage 变化保存快照到队列，页面退出时尽力发送最后快照。后台采集不会自动打开网页。
- 自动页面拉取同一网站最多每 5 分钟请求一次；期间新页面从本机缓存恢复 LocalStorage。手动拉取立即请求。每轮后台也会检查远端；内容相同不重复写入或刷新网页。
- 上传失败保留本机队列，按设置间隔重试；进程重启后继续处理。队列按后端、账号和远程文件路径隔离；旧队列不会发送到新后端。新变化不会被较早一次上传的确认丢弃；无可用页面时优先保留队列中的最新 LocalStorage。
- 正常自动同步没有弹窗通知；打开扩展时可查看最近后台成功时间或待重试错误。Cookie 可在网站尚未打开时恢复，LocalStorage 需等待对应页面出现。
- 不依赖关闭事件，不拦截浏览器退出。未到下一次后台上传就完全退出或断电时，最后改动可能尚未到远程，需等本机下次启动重试；若要立即换电脑，可手动推送一次。后台调度也受休眠、网络和浏览器限制影响。
- 网站退出登录也可能影响远程快照；恢复只写入快照中列出的 Cookie/LocalStorage，不保证清除接收电脑残留数据。不要在两台电脑同时切换同一网站的不同账号。

## 加密与风险

Cookie、LocalStorage 中的会话令牌可能等同于账号登录凭证。任何获得同步文件明文的人都可能冒用登录。只同步自己的账号，只使用私人 WebDAV 目录，不要使用公共分享、公共 Gist 或他人服务器。

推荐在两台电脑的高级设置先开启 **Protobuf 编码**，再开启 **端到端加密**，填写相同的强加密密码，然后首次推送。使用原项目的 AES-256-GCM 与 PBKDF2。Protobuf/Base64 本身不是加密。启用加密但没有编码或没有密码时，本分支会拒绝上传，避免意外明文。开启加密不会自动重写已有文件，需重新推送；远程历史版本和备份可能仍保留明文。

WebDAV 密码与数据加密密码用途不同；丢失加密密码无法恢复远程文件。原项目的通用设置（含加密密码）及 Gist/KV 账号配置使用 `chrome.storage.sync`，可能随 Chrome 账号同步；本分支新增的 WebDAV 凭据单独使用本机存储。请同时保护 Google 账号、本机浏览器资料和服务器备份。

扩展继承了上游 Cookie、页面和所有网站访问权限，因为同步功能需要读写登录数据。请仅在可信浏览器中安装，避免公开源码仓库中放入真实凭据、Cookie 导出文件、浏览器个人资料或同步文件。此分支移除了源码中的会话数据调试输出。

小红书、抖音等网站可能绑定设备、IP、浏览器指纹或要求二次验证。Cookie 同步**不保证**保持登录，不保证规避风控、扫码验证或异地登录限制。IndexedDB、SessionStorage、设备凭据及分区 Cookie 等并不保证被原有同步格式完整覆盖。

## 常见错误

| 提示 | 处理 |
| --- | --- |
| 401 | 检查用户名、密码或应用密码；确认服务器支持 Basic Auth |
| 403 | 检查目录权限和服务器访问策略 |
| 404 / 409 写入失败 | 先创建父目录，确认 URL 是 WebDAV 接口 |
| 412 冲突 | 先刷新远程列表确认数据；AList/OpenList 可在了解并发覆盖风险后手动开启兼容模式；仍报错需检查服务器锁和网关 |
| 测试文件清理失败 | 检查 DELETE 权限，手动删除 `.connection-test-…` 文件 |
| 解码／解密失败 | 检查同步文件内容和两端加密设置，不要直接覆盖未知文件 |
| 拉取后仍未登录 | 确认同一主机名并手动刷新；按网站要求重新验证 |

## AList / OpenList 的 412 与管理页显示 0

HTTP 412 表示请求条件未满足，本次推送不算成功。管理页的数量来自本机已加载的同步数据，推送失败或尚未读取时显示 0，不能证明远程文件为空。

1. 更新扩展后在管理页点击“刷新远程列表”。该操作只读取同步文件并刷新列表，不向网站写入 Cookie。
2. 若使用 AList/OpenList 且标准模式持续出现条件写入 412，可在 WebDAV 设置中明确勾选“AList / OpenList 等网关兼容模式”，保存后测试连接，再推送。不要自动对所有服务器启用。
3. 兼容模式不发送 If-Match / If-None-Match；上传前会重新读取并校验远程内容，但无法保证两台电脑同时写入时的原子性。尽量采用一台主要发送、另一台主要接收。
4. 如果兼容模式仍返回 412，则可能是文件锁、代理或挂载存储的问题，并不能由停用条件头解决。请依据报错中的 GET / PUT 方法检查服务端日志。

1.5.1 将手动推送与后台读写串行处理，减少同一扩展自身竞争；管理页会显示最近一次推送失败原因，并支持刷新远程列表。连接测试也会验证已有临时文件的覆盖，而非只验证新建文件。

参考：[OpenList WebDAV 实现](https://github.com/OpenListTeam/OpenList/blob/main/server/webdav/webdav.go)。不同版本、挂载驱动及代理的行为可能不同，本分支未直连用户的实际服务器验证。

## 1.6.0 内容摘要与方向

采用浏览器原生 SHA-256 做内容比较（与 MD5 比较的用途一致）。摘要在明文、排序归一后的数据上计算，排除时间戳、User-Agent、设备 Cookie storeId；不能直接比较每次随机加密的密文。未改变时跳过 PUT、cookies.set 和 LocalStorage 写入；编码／加密策略变更仍要求实际上传。

自动任务记录按后端和站点隔离的上次基线。本机新变化上传，远端新变化恢复；两端都改变同一站点时保留队列并停止覆盖，提示人工选择。上传期间产生的后续变化会保留并更新其基线。手动推送／拉取可确认方向，但不要在两台电脑同时切换不同账号。

后续源码统一维护于本仓库。依赖、构建缓存与 ZIP 不放回源码目录；用户下载生产 ZIP，解压覆盖原安装目录后手动重新加载。基于 1.5.1 的 AList/OpenList 修复均保留。
